# pnpm eval —— 整份需求达标率

《计划 v3.0》§6.9 的收口标准是「优先量化」，§2.4 的四层意图控制里，澄清、蓝图、校验、修复能自动量的部分都在这里量。这个目录只回答一个问题：

> 给一句人话需求，成品有没有把需求里写死的东西全落实？

它**不**回答：界面好不好看、题目出得对不对、学生爱不爱做。那些不是指标能替代的。

## 一条命令

```bash
pnpm eval                                   # 默认 mock，不联网，演练链路与判据
pnpm eval -- --mode replay --set debug       # 复核既有录像（3 条）
node --env-file=D:/project1/.secrets/eval-live.env eval/run.mjs --mode live --label full
```

| 参数 | 作用 |
|---|---|
| `--mode mock\|replay\|live\|record` | 决定数据来源。**三种来源的结论不能混着说**（见下表） |
| `--set all\|debug\|holdout` | `debug` 是被反复看过的题（可以拿来调 Prompt），`holdout` 是留出集（只看不改） |
| `--only id1,id2` | 只跑指定需求 |
| `--limit N` | 只跑前 N 条，用于快速冒烟 |
| `--delay-ms N` | 每条之间歇 N 毫秒，给上游限流留余量 |
| `--timeout-ms N` | 单条超时，默认 120 秒；超时留在分母里 |
| `--label xxx` | 给这次运行起个名字，进目录名 |

产物落在 `eval/runs/<runId>/`：`report.md`（人看）、`report.json`（机器看）、`raw/<id>.sse`（SSE 原文，可逐条回放核对）。

## 三种来源分别能证明什么

| mode | 证明 | 不能证明 |
|---|---|---|
| `mock` | 链路通电、判据能跑通 | 任何模型质量。mock 是内置脚本，不管需求说什么都吐同一份 4 题表单，达标率必然是 0 —— 这是**判据没漏水**的旁证，不是失败 |
| `replay` | 既有录像能被同一把尺子复核 | 新实验。录像只有 3 条，且录自本地桩（`local-stub`），本身就达不到需求里的分值 |
| `live` | **模型能力**：这一组才代表 Prompt 版本的真实水平 | 稳定性。一次运行是一条时间线上的样本，改 Prompt 前后要各跑一次才能比 |

报告首页第一行写死来源，就是为了防止把 `mock` 的 0% 说成「模型不行」，或者把 `live` 的百分比说成「历史录像也没问题」。

## 判定分三层，只判需求里写死的

`eval/judge.mjs` 是纯函数：数据进、判定出，不读文件、不起服务、不看模式。这样才能保证两次运行的百分比可比。

| 层 | 查什么 | 依据 |
|---|---|---|
| blueprint | 表单类型、题量、题型分布、总分、知识点 | 需求文本里的显式数字与词 |
| validation | 问卷不许带 `answer` 与 `score`（R3/R5） | `packages/schema/src/rules.ts:214-232` 的原文 |
| capability | 这条需求在当前 schema 下能不能被表达 | 字段类型有没有对应的槽位（目前只有简答计分一条） |
| policy | 这条生成有没有真的走完门禁 | 由调用方传 `gateBlocked`，不在判定器里猜 |

两个刻意的口径，写在这里免得被当成疏漏：

1. **`meta` 不随事件流下发**（I2 契约如此），所以「总分」以逐题 `score` 合计为准；「知识点」以题干/选项文本里是否出现该关键词为证据，不假装看过 `meta.objectives`。
2. **澄清层没有可自动判的东西**。产品当前不追问缺槽位需求，`c01`/`c02` 两条探针只记录「没追问」这个事实，不计入达标率分母。这一层的数字就是 0，不许用别的东西补。
3. **`capability` 层不是给产品开后门**。它只用来标记「这条需求在当前结构下无解」——目前唯一一类是「简答也计分」：`shortFieldSchema`（`packages/schema/src/types.ts:99`）继承 `baseFieldSchema`，没有 `score` 字段，所以需求写「含 2 道简答、每题 5 分、共 40 分」时，成品最多凑出 30 分。这类条目**仍然计在主指标分母里、仍然算未达标**，只是额外给一份「可表达子集达标率」，让读者能分清是模型没做到还是产品没这个语义。

## 两个口径，别只看一个

| 口径 | 回答什么 | 什么时候用 |
|---|---|---|
| 整份达标率（主） | 全部判分需求里，成品完全满足需求的比例 | 对外报数就用这个，分母最硬 |
| 可表达子集达标率（副） | 在**产品能表达**的需求上，模型做到多少 | 定位问题归属：主指标低但子集高 = 产品缺语义，不是模型笨 |

两个数一起给，谁也不掩盖谁。只报子集会被说成挑好数据，只报主指标会把产品缺口记成模型能力。

## 分母纪律

跑了几条判分需求，分母就是几条。以下情况**都留在分母里，按未达标算**：

- 传输失败 / 超时 / 服务端 5xx
- 一条字段都没通过校验（成品为空）
- 整表门禁拦下（`llm_invalid_output`）
- 录像未命中（`llm_config`）

「结构完全匹配」这个指标另有资格线：必须有蓝图层判定才参与，空成品不参与——否则「没产出」会被洗成「结构对了」。报告里 `无任何成品` 单独一行计数。

## 需求集

`eval/requirements.jsonl`，一行一条，由 `eval/gen_requirements.py` 生成后手工校过。字段：

```json
{"id":"q03-refraction","set":"debug","judgeable":true,"requirement":"初二物理《光的折射》课堂检测，5 道题：3 道单选、2 道填空，共 25 分，每题 5 分。","expect":{"kind":"quiz","count":5,"types":{"single":3,"fill":2},"totalScore":25}}
```

- `set=debug` 16 条（含 3 条预置需求）：调 Prompt 时反复看的就是这些，**别拿它报成绩**。
- `set=holdout` 14 条：12 条判分 + 2 条澄清探针。改 Prompt 时不看细节，只在跑分时看总数。
- 需求集 sha256 写进报告。改一个字节就是另一把尺子，报告之间不再可比。

## 判定器版本

`fitness.v3`。改口径必须同时改 `JUDGE_VERSION`（`eval/judge.mjs:23`），否则新旧报告会被当成同一把尺子比。

v2 → v3 改了两处，都是「尺子比产品更严」的修正：

1. 问卷检查曾在 `answer`/`score` 之外还禁 `explanation`/`bloom`/`knowledgePoint`。产品规则（`rules.ts:214-232`）只禁前两个，后三者是 schema 允许的字段（`publicView` 会剥掉）。实测误伤 3 条问卷。
2. 新增 `capability` 层：把「产品结构表达不了」和「模型没做到」分开计数，主指标口径不变。

## 判据不是「答得对不对」

`fitness.v1` 只看结构。题目内容对不对、难度合不合适、选项像不像样，机器判不了，得靠 `pnpm eval` 之后的人工抽查（`raw/<id>.ndjson` 里逐字段读）。所以报告里没有任何「质量分」，只有「需求履行率」。

改判定口径必须同时改 `JUDGE_VERSION`（`eval/judge.mjs` 顶部），否则新旧报告会被当成同一把尺子比。

## 已知限制

1. **澄清层为 0**：产品没有追问机制（`c01`/`c02` 两条探针证明它直接开生成），这一层的量化等追问上线后才有意义。
2. **简答计分是产品缺口，不是评测口径问题**：`short` 字段没有 `score`，教师声称「共 40 分」而发布出去的卷子满分只有 30 分。修法在 schema 侧（让 `shortFieldSchema` 也带 `score`），不在评测侧。改完要同步 `rules.ts` 的 `isScoredItem`、判分、`publicView` 与 web 渲染，并升 `schemaVersion`。
3. **一次运行 = 一条时间线**：`live` 的百分比有采样波动，比较 Prompt 版本时至少要各跑两轮再看方向，别拿单次 100% 当期终结论。
4. **限流要放开**：评测连打几十条，`RATE_GENERATE_PER_MIN` 被 runner 设成 1000。线上阈值是 10/分钟（见 `server/src/env.ts`），两者不是一回事。
5. **知识点评判靠关键词**：换了说法（「顶点」vs「顶点坐标」）会判缺失，这是刻意的保守——宁可漏判达标，不要放过不达标。

## 与其它证据的分工

| 要证明的事 | 用哪个 |
|---|---|
| 一条链能不能跑通（HTTP 语义） | `node scripts/verify.mjs`（VC1–VC5） |
| 界面能不能点（真浏览器） | `node scripts/browser-closed-loop.mjs`（七步九图，含教师批改） |
| 需求有没有被满足（结构层面） | `pnpm eval`（本目录） |
| 题目内容好不好 | 人看 `raw/*.ndjson`，机器不判 |
