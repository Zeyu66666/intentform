## 开工前写清的四件事（纪律 4.0 第 1 条）

| 项 | 内容 |
|---|---|
| 目标 | 负责人的原始诉求：「生成的试卷应该先保存，等修改完全之后再发布」。此前生成页只有一个「保存并发布」按钮，会把刚生成、还没检查的卷子直接推给学生；编辑器只能存草稿，没有发布入口 |
| 取舍 | 生成页只保留「保存为草稿」，保存后给「去编辑并发布」入口；发布按钮移到编辑器底栏。有未保存改动时发布禁用并提示「先保存当前改动，再发布」；发布成功后表头显示学生链接与「已发布当前草稿」。发布仍是显式动作，不做自动发布，也不在生成页保留第二条发布路径 |
| 验收案例 | ①生成页不再出现「保存并发布」，点「保存为草稿」后出现草稿版本与编辑器入口；②编辑器无改动时可发布，发布后出现 `/f/<slug>` 学生链接；③编辑器有未保存改动时发布禁用并给出原因；④保存出新草稿后发布按钮重新可用，发布快照包含生成页就地改过的题干；⑤问卷复用同一条保存/发布链路；⑥闭环 19 步全绿，`pnpm check` 与 `verify.mjs` 全绿 |
| 停止条件 | 生成页偷偷自动发布、编辑器发布未保存的旧版本、为了两次请求在服务端新增「发布最新草稿」语义（发布必须显式带 `versionId`）、或让闭环继续走「生成页一键发布」的旧路径 |

## 实现要点

| 层 | 落点 | 关键决定 |
|---|---|---|
| 生成页 | `web/src/publish/SaveDraftPanel.tsx`（原 `PublishPanel`） | 只调 `createForm`，不调 `publishForm`；保存后展示草稿版本 + 「去编辑并发布」+「回看板」。失败视图复用 `describePublishFailure`，401/400 口径不变 |
| 编辑器 | `web/src/edit/EditorPage.tsx` | 底栏新增「发布」：`publishForm(formId, { versionId: edit.baseVersionId })`；`plan.hasChanges` 时禁用并提示先保存；已发布当前草稿时按钮变「已发布」；发布成功后更新本地 `form.slug/publishedVersionId`，表头出现学生链接 |
| 口径 | `publish-flow.ts` | 发布请求显式带版本 id，不接受「发布最新草稿」；`toPublishedForm` 改由编辑器复用，学生路径仍只从 `API_PATHS.fill()` 取 |
| 闭环 | `scripts/browser-closed-loop.mjs` | 第 3 步改为真实两步：点「保存为草稿」→ 等「去编辑并发布」链接 → 进编辑器点「发布」→ 抓 slug；问卷步骤复用同一函数。保存按钮不存在时才退回 API，存在但后续失败必须抛错 |

## 我如何引导 AI 修复问题

本轮抓到的真实问题：

1. **闭环脚本还活在一键发布的世界里**。旧第 3 步检测「页面上有没有发布按钮」，找到就点；改成保存草稿后它会静默退回 API，等于新链路一条都没测。改成 `saveDraftAndPublishViaEditor()`：有保存按钮就必须走完保存 → 编辑器 → 发布，任一环节失败直接抛错；只有旧构建完全没有保存按钮才走 API 兜底。
2. **问卷步骤复制了旧的发布逻辑**。第 10 步自己找「发布」按钮、自己抓 slug；保存/发布拆开后这段会永远失败。删掉重复逻辑，与第 3 步共用同一个 helper，问卷和新链路一起被覆盖。
3. **「保存中…」跑到了发布按钮上**。发布和保存共用一个 `busy`，发布时保存按钮显示「保存中…」，读起来像状态错了。加独立的 `publishing` 状态：保存按钮只在真正保存时显示「保存中…」，发布按钮显示「发布中…」。
4. **新测试文件放错扩展名，vitest 根本没跑**。`SaveDraftPanel.test.tsx` 不符合 `vitest.config.ts` 的 `*.test.ts` 约定，第一次运行只报了 publish-flow 的 12 条用例。改成 `.test.ts` 后两个静态渲染用例才真正执行。
5. **`git add` 旧文件名失败**。文件改名后仍按旧路径 `git add`，得到 `pathspec did not match`；改用 `git add -A web/src/publish` 让 Git 自己识别删除/新增。

自己否决的：

- **生成页保留「保存并发布」快捷入口**：会绕开「先检查再发布」的初衷，教师仍可能一键推错卷。
- **编辑器发布时自动先保存**：两次请求合并成一个按钮，教师看不到自己发的是哪一版；显式「先保存、再发布」把版本边界摆在界面上。
- **服务端新增「发布最新草稿」接口**：会破坏「发布请求显式带 `versionId`」的契约，也让并发编辑下的发布目标变得含糊。
- **在生成页自动创建草稿**：每次生成都落库会产生大量废弃表单；保存必须是教师动作。
