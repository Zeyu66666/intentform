## 动作整理（按发生顺序）

1. **读计划与现状**：确认 I6 不是「再写一批测试」，而是「造一把能量出意图控制效果的尺子」。
   查仓库：`/api/generate` 已能被脚本直接调用（`LLM_MODE=replay|mock|live|record`），SSE 契约已冻结，
   缺的是「需求 → 成品 → 判定」这一层。
2. **确认上游可用性**：先探 live 模式能不能连通。第一次用随手填的 Key，12 条需求全部 401，
   报告生成出「0/28」。处置：不改判定器，改报告——第 3 行固定打印「数据来源」，
   让「真跑过 / 回放 / mock」一眼可辨。
3. **写需求集**：`eval/gen_requirements.py` 从 `packages/schema/src/presets.ts` 与 `web/src/presets.ts`
   的原文生成 `eval/requirements.jsonl`，30 条 = 16 debug（含 3 条界面预置，调 Prompt 时反复看）
   + 14 holdout（12 条判分 + 2 条缺槽位探针）。程序化生成的理由：回放键含需求原文哈希，手抄会全部未命中。
4. **写判定器**：`eval/judge.mjs`，四层判定——blueprint（类型/题量/题型/总分/知识点）、
   validation（问卷不许带 `answer`/`score`，对齐 `rules.ts` 的 R3/R5）、capability（当前 schema 能否表达）、
   policy（有没有走完行级校验与整表门禁）。纯函数，无 IO，便于单测。
5. **写编排**：`eval/run.mjs`，自起服务、逐条打 `/api/generate`、落 SSE 原文、出 `report.md` + `report.json`。
   分母固定，超时 / 空成品 / 门禁拦截 / 录像未命中全部计入。
6. **第一版判定器跑出 25/28，当场判定不可信**：明细里 25 条成品是空的。反查判定树，
   发现蓝图判定对空数组 `every` 为真。修法：蓝图层要求「N 条判定齐全且全过」，缺条即不合格。
   AI 第一版建议「空成品跳过不计数」，被否——那会把分母从 28 压到 3，属口径操纵。
7. **第二版跑出误伤**：`q16`/`q17`/`q23` 被判「问卷带答案」，但它们只有 `bloom` 与 `knowledgePoint`。
   对照 `packages/schema/src/rules.ts:214-232`，产品只禁 `answer`/`score`；判定器把
   「`publicView` 会剥的字段」错当成「不许存在的字段」。修法：违规键表与 `rules.ts` 同源，并在注释里指回行号。
8. **判定器升 v3 + 补口子**：`JUDGE_VERSION` 升到 `fitness.v3`，并约定「改口径必须同时改版本号」，
   否则新旧报告会被当成同一把尺子比较。配 24 条单测（`eval/judge.test.mjs`），盯三个方向：
   空成品、误伤合法字段、平均偏差被空成品稀释。
9. **跑真测**：`LLM_MODE=live`，30 条，142.3 秒。结果 42.9%（12/28），可表达子集 92.3%（12/13），
   题量偏差 0.00 题，错行 8 个全 `E_SURVEY_HAS_ANSWER` 且修复环 8/8 救回。跑完把 15 条无解需求
   对照 schema 逐条核过，确认是「简答字段没有分值」这一个结构性原因，不是 15 个不同原因。
10. **入库与文档**：`docs/evidence/eval/` 放人看的 README 与机器看的 json（剔掉成品全文，65 KB）；
    `eval/runs/` 进 `.gitignore`；作品介绍文档第 3 章新增 3.4 节并改 3.1/3.3/附录 A/B 的数字；
    计划 v3.0 的迭代表下补 I6 完成状态与实测值。
