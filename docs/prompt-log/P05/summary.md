## 提问

这一轮的提问很短：`继续I6`。约束是我自己在计划里定死的（《计划 v3.0》§4.1 I6 行 + §6.9「优先量化」）：

- 交付物是**指标**，不是功能。四层意图控制（澄清 / 蓝图 / 校验 / 修复）里能自动量的都要有数。
- 主指标是「整份需求达标率」，分母口径必须硬：超时、空成品、门禁拦截、录像未命中**都留在分母里**，不许挑。
- 不许用 mock 报数，也不许把「链路跑通」说成「模型答得好」。
- 一次运行的报告要能入库（评审不装环境也能看数），原始事件流不入库（可重跑生成）。

## AI 修改建议

1. **建 `eval/` 独立目录，不塞进 `packages/llm`**。采纳。理由：评测器要同时依赖 schema 的规则与服务端的 HTTP 行为，塞进任何生产包都会把「测试用代码」变成线上依赖；独立目录还能在 `vitest.config.ts` 里单独 include，不影响四个包的构建产物。
2. **需求集从 `presets.ts` 的原文程序化生成**（`eval/gen_requirements.py`），不手抄。采纳，且是这轮最划算的一个决定：回放键是「需求原文 + 模型 + prompt 版本 + schema 版本」的哈希，手抄差一个标点就全部未命中，现场表现为「录像全部 miss」，会被误读成管线坏了。30 条需求里 3 条直接取自 `GENERATE_PRESETS`，就是为了跟界面预置按钮对齐。
3. **用 LLM 当裁判（LLM-as-judge）来评「题目好不好」**。否决。理由：本项目的评测要证明的是「结构是否满足需求」，这是可判定的（题量、题型、分值、知识点、问卷有无答案）；一旦引入 LLM 裁判，报告里的每个百分比都变成「另一个模型的意见」，而我这轮恰恰要证明的是数字可信。题目质量留到人工评分表（已写进文档 3.5 与附录 A）。
4. **只报「可表达子集」的 92.3%**（因为 15 条需求在 schema 下无解，看起来像产品锅）。否决，但把子集数并列报出。理由：只报高的那个是挑数据；只报低的那个把产品缺口记成模型能力。两个口径一起给，并写明差异来源（简答字段没有分值），让读者自己判断。
5. **改 Prompt v2 把达标率刷上去**。否决，且用数据支撑：可表达子集已经 92.3%、题量偏差 0.00 题、题型只偏 1 条——瓶颈不在 Prompt，动它是在已经及格的地方刷分，还会让 3 条回放录像（键里含 prompt 版本）全部失效。结论写进文档 3.4 的收尾段。
6. **用 `node:test` 而不是 vitest 写判定器测试**。否决。仓库其余 52 个测试文件都是 vitest，混两套跑法会让 `npx vitest run` 的「全绿」失去意义。
7. **把 30 条需求的成品全文一起入库**。否决。`report.json` 剔掉 `form` / `expect` 后 65 KB 即可入库；成品全文在 `eval/runs/*/raw/*.sse`，`eval/runs/` 已 gitignore，需要时重跑生成。

## 我如何引导 AI 修复 Bug

这轮没有产品 bug，抓到的是**尺子自己的 bug**——比产品 bug 更危险，因为量具偏了，后面所有数字都不作数。两处都是我自己对着输出反查出来的，不是跑测试跑出来的：

1. **空成品被判成「结构完全匹配」，0/28 报成 25/28。**
   现象：第一次跑出 25/28，但明细里 25 条的「成品」是空的。
   定位：翻判定树，蓝图层写的是 `checks.filter(c => c.layer === "blueprint").every(c => c.ok)`；空成品没有产出任何字段，蓝图检查一条都没生成，`every` 对空数组为 `true`。
   修法：蓝图层先判「必须有 N 条蓝图检查且全部通过」，条数不齐直接判不合格（`missing-blueprint-checks`）。给 AI 的上下文就是这一行判定代码 + 一条空成品记录，要求它**先说出「为什么 25 条能过」再改**——它第一版改的是「把空成品跳过不计数」，那样分母就从 28 掉到 3，正是我要防的口径操纵，被我否掉。
   回归：`eval/judge.test.mjs` 里专门留一条「空成品必须判不合格」，注释写明这一版前身是 25/28。

2. **问卷检查比产品更严，误伤 3 条合格问卷。**
   现象：`q16` / `q17` / `q23` 被判「问卷带答案」，但成品里只有 `bloom` 与 `knowledgePoint`。
   定位：产品规则 `packages/schema/src/rules.ts:214-232` 只禁 `answer` 与 `score`；判定器却把 `bloom` / `knowledgePoint` 也列进了违规键——`publicView` 会剥这两个字段（`04c0e6f`），但那是「不对外暴露」，不等于「表单不许有」。判据被我写错成「学生看不到的字段都不该存在」。
   修法：判定器的违规键表改成与 `rules.ts` 同一份来源（写成常量并在注释里指回 `rules.ts` 行号），只禁 `answer` / `score`。
   回归：补一条「问卷可带 bloom/knowledgePoint，但不可带 answer/score」。

两处修完，判定器版本号从 `fitness.v2` → `fitness.v3`，并强制「改口径必须同时改 `JUDGE_VERSION`」，否则新旧报告会被当成同一把尺子比较。测试从 566 涨到 590（24 条判定器单测）。

顺带一个真实的小事故：第一版编排用了 `LLM_MODE=live` 但 Key 是随手填的，12 条需求全部 401，`report.md` 生成出来是「0/28」。当时的正确处置不是改判定器，而是**让报告在开头就写清数据来源**（`数据来源：真实上游 / 回放 / mock`），这样一眼能看出是不是真跑过——这一栏现在是 report 的第 3 行。
