## 主结果

| 口径 | 数值 | 怎么读 |
|---|---|---|
| 整份达标率 | **42.9%**（12/28） | 全部判分需求里，成品完全满足需求的比例。分母最硬，对外就报这个 |

## 三个结论

1. **题量与题型不是瓶颈**。平均偏差 0.00 题，28 条里只有 1 条题型跑偏（`preset-bio-survey`：要 3 单选 + 2 量表 + 2 填空 + 1 简答，模型给了 6 道简答）。
2. **卡住主指标的是产品缺语义，不是模型**。15 条需求写了「含 N 道简答、每题 5 分、共 M 分」，而 `short` 字段在 schema 里没有 `score`（`packages/schema/src/types.ts:99`，`shortFieldSchema` 继承 `baseFieldSchema`）。模型把客观题该给的分都给了、简答也给不出分，于是总分永远差 5 或 10 分。去掉这一组，13 条里过 12 条。
3. **修复环是有效的，而且有据可查**。3 条问卷（`q16`/`q17`/`q23`）首轮把 `answer` 或 `score` 带进了问卷字段，被 R3/R5 判为错行，修复钩子只回喂出错字段、第二轮改好后通过。错行 8 个、救回 8 个，没有一条卡死。

## 两个口径为什么都要报

只报 42.9% 会把产品缺口记成模型能力问题；只报 92.3% 像在挑数据。分母里那 15 条不改判定口径、不剔除，另给一份子集数——读者自己判断该怪谁。

## 这次量化顺带抓到的两个「尺子」缺陷

数字要可信，先得确认尺子没骗人。第一版判定器（`fitness.v2`）有两处会往好看的方向错，都是这一轮发现并修掉的，都有回归测试（`eval/judge.test.mjs`，24 条）：

1. **空成品被算成「结构完全匹配」**。原来判蓝图层用 `every(check => check.layer !== "blueprint" || ok)`，而没有产出的条目只有一条 `policy/form-present` 判定，`every` 直接为真——实测把 25 条空成品算成结构匹配，`0/28` 报成 `25/28`。
2. **问卷检查比产品更严**。原来把 `bloom` / `knowledgePoint` 也算违规，而产品规则（`packages/schema/src/rules.ts:214-232`）只禁 `answer` 与 `score`。实测误伤 3 条合格问卷。

两处都是「尺子偏松」或「尺子偏严」的方向性错误，不是笔误；判定器版本号因此从 `v2` 升到 `v3`，改口径必须同时改 `JUDGE_VERSION`，否则新旧报告会被当成同一把尺子比。

## 没做的事（不写成就）

- **没改 Prompt**。可表达子集 92.3% 说明 Prompt 当前不是瓶颈，`Prompt v1→v3` 的迭代留到 I7 之后，等简答分值补齐再谈。
- **没修 schema 的简答分值**。这条要动 `shortFieldSchema`、`isScoredItem`、判分、`publicView`、web 渲染与 `schemaVersion`，属于产品变更，不在量化迭代的边界里。
- **澄清层仍是 0**。`c01`「帮我出一份英语卷子」、`c02`「做个问卷」两条探针证明产品直接开生成、不追问缺槽位。这一层的量化等追问上线后才有意义。
